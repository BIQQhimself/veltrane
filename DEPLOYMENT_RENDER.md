# Deploying VELTRANE on Render (free tier)

This guide prepares the repository for Render's free tier: a **Static Site** for the Next.js
frontend and a **Web Service** for the FastAPI backend, both in one Blueprint (`render.yaml`).
Nothing here is executed automatically — the deployment is started from the Render dashboard by
the repository owner.

Read [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md) before treating the result as a production
system. Render's free tier is a demonstration and pre-launch target: it sleeps when idle, its free
database expires, it has no managed backups and it cannot host a background worker.

## What the blueprint creates

| Resource | Type | Plan | Purpose |
| --- | --- | --- | --- |
| `veltrane-web` | Static Site | free | Next.js static export (`frontend/out`) served at `corvex.fun` and `www.corvex.fun` |
| `veltrane-api` | Web Service (Python) | free | FastAPI + uvicorn, migrations at start, served at `api.corvex.fun` |
| `veltrane-db` | PostgreSQL | free | Primary data store, reachable only from inside Render |

Marketing copy, pricing and brand assets live in the frontend; no secrets are baked into it.
`NEXT_PUBLIC_API_URL` is public by design and only names the API origin.

## Prerequisites

1. Repository `BIQQhimself/veltrane` on GitHub with `render.yaml` at the root (already committed).
2. A Render account (free, no card required for free-tier services).
3. DNS control for `corvex.fun`.
4. Two generated secrets, produced locally and never committed:

   ```bash
   python -c "import base64,os; print(base64.b64encode(os.urandom(32)).decode())"  # master key
   ```

   `VELTRANE_SECRET_KEY` is generated by Render (`generateValue: true`). The master key is not,
   because it has a fixed shape (base64 of exactly 32 bytes) and Render's generator does not
   guarantee that shape.

## Step 1 — Create the Blueprint

1. Render dashboard → **New** → **Blueprint**.
2. Select the `BIQQhimself/veltrane` repository and branch `main`.
3. Render reads `render.yaml` and shows three resources plus one prompt:
   - `VELTRANE_MASTER_ENCRYPTION_KEY` — paste the base64 key you generated.
   - `VELTRANE_REDIS_URL` (optional) — leave empty, or paste an Upstash free-tier Redis URL
     (`rediss://default:...@...upstash.io:6379`). Without it the API still runs; rate limiting
     falls back to per-process counters and market data is cached per process.
4. **Apply**. The API build installs `backend/requirements.txt`; the start command runs
   `alembic upgrade head` and then uvicorn.

The API refuses to start in production when `VELTRANE_SECRET_KEY` is weak, `VELTRANE_COOKIE_SECURE`
is false, billing is `mock`, or the master key is missing. A failed deploy is the guard working,
not a bug: read the log line.

## Step 2 — Verify the API hostname

Render assigns `veltrane-api.onrender.com`. Check it before touching DNS:

```bash
curl -sS https://veltrane-api.onrender.com/api/v1/health
curl -sS https://veltrane-api.onrender.com/api/v1/ready
curl -sS https://veltrane-api.onrender.com/api/v1/config
```

`/api/v1/health` answers `{"status":"ok"}` and is the platform health check. `/api/v1/ready` adds a
database probe. `/api/v1/config` must report `live_trading_enabled: false` and
`billing_provider: "off"`.

The first request after a sleep can take 30–60 seconds; the browser client retries `502/503/504`
and network failures twice before showing an error.

## Step 3 — Custom domains and DNS for `corvex.fun`

Add the domains in Render first, then the DNS records Render shows. With this blueprint:

| Hostname | Render service | DNS record at your DNS provider |
| --- | --- | --- |
| `corvex.fun` | `veltrane-web` (Static Site) | Apex alias: `ALIAS`/`ANAME` → `veltrane-web.onrender.com` (or a flattened `CNAME` if your provider supports it) |
| `www.corvex.fun` | `veltrane-web` (Static Site) | `CNAME` → `veltrane-web.onrender.com` |
| `api.corvex.fun` | `veltrane-api` (Web Service) | `CNAME` → `veltrane-api.onrender.com` |

Notes:

- **Apex records.** Standard DNS forbids a `CNAME` at the zone apex. Use your provider's alias
  record (Cloudflare "flattened CNAME" with the proxy **off**, Route 53 alias, NS1/`ALIAS`,
  DNSimple `ALIAS`, Bunny/`ANAME`). If your provider has none, point the apex at `www` with a
  redirect and serve the app at `www.corvex.fun`.
- **Cloudflare.** Keep the records **DNS only** (grey cloud) until Render has issued the
  certificate, then decide whether to proxy. Render terminates TLS itself; double-proxying adds a
  second TLS hop and hides the real client address from the API.
- **Leave the platform hostnames alive.** `*.onrender.com` stays reachable and is what Render uses
  for its own checks.
- **Do not add a wildcard record** unless you mean it: `*.corvex.fun` would also catch `api`.

HTTPS certificates are issued automatically by Render once DNS resolves to the service and the
domain shows **Verified**. No certificate work is needed on your side; HSTS is already sent by the
Static Site headers.

## Step 4 — Production networking, cookies and CORS

These values are already set by the blueprint. They matter because the web app and the API are on
different subdomains of the same registrable domain:

| Setting | Value | Why |
| --- | --- | --- |
| `VELTRANE_CORS_ORIGINS` | `https://corvex.fun,https://www.corvex.fun` | Server-side allowlist with credentials; no wildcard is possible with `allow_credentials=True` |
| `VELTRANE_COOKIE_SECURE` | `true` | HTTPS only |
| `VELTRANE_COOKIE_SAMESITE` | `lax` | `corvex.fun` and `api.corvex.fun` share a site, so Lax cookies are sent on the cross-origin XHR. `none` would also work but weakens CSRF posture and requires `Secure` |
| `VELTRANE_WEB_BASE_URL` | `https://corvex.fun` | Verification and reset links point at the site, not the API |
| `VELTRANE_API_BASE_URL` | `https://api.corvex.fun` | Absolute API links in email and docs |
| `VELTRANE_TRUSTED_PROXIES` | `*` | Render's proxy is the only path into the process; without this every visitor shares one rate-limit bucket. The API is not reachable directly |
| `NEXT_PUBLIC_API_URL` | `https://api.corvex.fun` | Baked into the static bundle at build time |

The refresh cookie is `HttpOnly` and `SameSite=Lax`; state-changing requests additionally require
the `X-CSRF-Token` header, so a cross-site request cannot ride the cookie alone.

If you later move the site to a different registrable domain from the API (for example
`veltrane.app` + `api.veltrane.fun`), switch `VELTRANE_COOKIE_SAMESITE` to `none` and keep
`VELTRANE_COOKIE_SECURE=true`, then update `VELTRANE_CORS_ORIGINS` and rebuild the static site so
`NEXT_PUBLIC_API_URL` matches.

## Step 5 — Post-deploy smoke test

Run these against the public hostnames; each one is a check, not a screenshot.

```bash
# 1. API liveness and configuration
curl -sS https://api.corvex.fun/api/v1/health
curl -sS https://api.corvex.fun/api/v1/config

# 2. CORS preflight from the site origin
curl -sS -i -X OPTIONS https://api.corvex.fun/api/v1/auth/login \
  -H "Origin: https://corvex.fun" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type" | grep -i "access-control"

# 3. Static site + security headers
curl -sS -I https://corvex.fun/ | grep -iE "strict-transport|x-frame|x-content-type"
curl -sS -o /dev/null -w "%{http_code}\n" https://corvex.fun/login/
curl -sS -o /dev/null -w "%{http_code}\n" https://corvex.fun/app/terminal/

# 4. Live trading and payments are off
curl -sS https://api.corvex.fun/api/v1/config | grep -E "live_trading_enabled|billing_provider"
```

Then in the UI:

1. Register an account. In production with no email provider wired, the verification email is only
   written to `email_outbox`; see the blocker below.
2. Sign in, confirm the Overview and Markets pages label data correctly (`ccxt` public market data,
   demo/paper badges where they apply).
3. Open **Admin → Risk** as an owner and confirm **Live trading master switch** shows
   `Operator key: disabled` — the switch cannot enable live trading while the deployment flag is
   off, and the API answers `400 deployment_flag_off` if you try.
4. Confirm a plan upgrade attempt returns a clear `billing_disabled` message rather than granting
   the plan.

## Known blockers on this tier (read before announcing a launch)

- **Email delivery.** No SMTP/API provider is wired, so verification and reset emails are queued,
  not sent. Either wire a provider into `backend/app/services/email.py:deliver_queued` (Resend,
  Postmark and SES all have free or near-free tiers) or run with
  `VELTRANE_REQUIRE_EMAIL_VERIFICATION=false` and accept unverified signups. Do not claim email
  verification works until delivery is real.
- **Free Postgres expires.** Render deletes free databases 30 days after creation. Migrate to a
  paid instance, or point `VELTRANE_DATABASE_URL` at a free-tier managed Postgres (Neon,
  Supabase) that supports persistent storage, before the window closes.
- **No backups.** Free instances have no managed backups; `pg_dump` from a scheduled job is the
  only recovery path. See [DEPLOYMENT.md](DEPLOYMENT.md#backups).
- **Idle sleep.** Free web services sleep after ~15 minutes without traffic. The first request
  afterwards takes 30–60 seconds; the scheduler therefore does not tick while asleep, so paper
  sessions advance only when the service is awake.
- **Single instance.** The in-process paper-trading scheduler must stay on exactly one instance.
  Render free tier runs one, which is why `VELTRANE_SCHEDULER_ENABLED=true` is safe here.
- **No Redis by default.** With `VELTRANE_REDIS_URL` empty, rate limiting is per process and the
  market-data cache is per process. Kill switches, entitlements and live-trading gates are all
  database-backed, so their behaviour is unaffected.
- **750 instance hours / month.** One always-on free web service is roughly 730 hours; a second
  free web service (or a long-running preview) will exhaust the quota.
- **Build minutes and build memory.** Free builds are capped; `npm ci` plus `next build` for this
  app fits, but keep the frontend dependencies lean.

## Operating notes

- **Deploying a change.** Push to `main`; Render rebuilds both services. The API runs migrations at
  start, so a migration that is not backward compatible will fail the deploy and leave the previous
  version serving traffic (Render keeps the old instance until the new one is healthy).
- **Changing a secret.** Edit it in the Render dashboard → Environment, then trigger a manual
  deploy. Rotating `VELTRANE_MASTER_ENCRYPTION_KEY` makes stored credential envelopes unreadable;
  see [SECURITY.md](SECURITY.md) before doing it.
- **Rollback.** Render keeps previous deploys: **Events → Deploy → Rollback**. Database migrations
  are not rolled back automatically; a broken migration needs a forward fix.
- **Logs.** Structured JSON on stdout, visible in the dashboard. No log retention beyond the free
  window, so anything you need to keep must be exported.
- **Custom domains are not required to test.** Everything except cookie-origin behaviour works on
  the `onrender.com` hostnames, but `VELTRANE_CORS_ORIGINS` and the static build's
  `NEXT_PUBLIC_API_URL` must match whichever hostnames you actually use.

## Free-tier cost

Free. No paid add-ons are required by this blueprint, and nothing in the repository calls a paid
API at runtime. Going to production would need, at minimum, a paid database with backups, an email
provider, a Redis instance for shared rate limiting, and a payment processor.
